# Architecture & Design Decisions

This document captures the non-obvious design decisions in this project, along with
the reasoning and trade-offs behind each one. Every entry follows the same structure:
**What** was chosen, **Why**, the **Trade-off**, and **When to reconsider**.

---

## 1. HTTP 301 Redirect (Moved Permanently)

**What:** Short URL redirects respond with HTTP 301 (Moved Permanently).

**Why:** A 301 tells the browser *"this redirect is permanent — cache it and don't
ask the server again."* This has two benefits:

- **Speed** — repeat visits resolve instantly from the browser's cache with zero
  network latency.
- **SEO** — search engines transfer ranking ("link equity") from the short URL to
  the original URL.

**Trade-off:** Because the browser caches the redirect, it never contacts the server
again for that short URL. This means the click tracker only sees the *first* visit
per browser. If per-visit analytics matter more than raw speed, we can switch to
HTTP 302 (Found), which forces the browser to check with the server every time.

**When to reconsider:** If accurate per-visit analytics becomes a requirement (e.g.,
tracking every individual click matters more than redirect latency).

---

## 2. Async Click Tracking (Fire-and-Forget Channel)

**What:** When a redirect happens, the click isn't written to the database
immediately. Instead, the short code is dropped into a Go buffered channel, and a
background goroutine picks it up later to write to the DB.

**Why:** Writing to the database takes time (network round-trip + disk I/O). If we
did it during the redirect, the user would have to wait longer. By queuing the click
in memory, the redirect completes in under 1ms and the DB write happens
asynchronously in the background.

**Trade-off:**

- If the server crashes before the background goroutine processes the queue, those
  clicks are **lost forever** — they only existed in memory.
- If the channel is full (see [Buffer Size](#3-channel-buffer-size--1000)), new
  clicks are **silently dropped** with only a log warning.

**When to reconsider:** If 100% click accuracy is required, we can replace the
in-memory channel with a durable message queue (e.g., Kafka, RabbitMQ) that
persists events to disk before acknowledging them.

---

## 3. Channel Buffer Size = 1000

**What:** The buffered channel that queues click events holds at most 1000 pending
items before it starts dropping new clicks.

**Why:** The buffer needs to be large enough to absorb bursts of traffic while the
background goroutine writes each click to the DB (each write takes a few
milliseconds). 1000 was chosen as a reasonable starting heuristic for a small service.

**Trade-off:**

- **Too small** → clicks get dropped during traffic spikes.
- **Too large** → uses more memory, and delays can pile up.
- There is currently **no monitoring** to know if clicks are being dropped in
  production.

**When to reconsider:** We can add alerting on the `"click tracker channel full"`
log message, then tune the buffer size based on real traffic patterns.

---

## 4. Redis Cache TTL = 1 Hour

**What:** When a short URL mapping is cached in Redis, it expires after 1 hour.

**Why:** Even though URL mappings never change (a short code permanently maps to
the same original URL), we don't want Redis to grow unbounded with entries that may
never be visited again. The TTL ensures stale/unused entries are cleaned up
automatically.

**Trade-off:** After the cache expires, the next visit for that short URL will be
slower because it has to query the database. A longer TTL (e.g., 24 hours) would
mean more cache hits but higher Redis memory usage.

**When to reconsider:** If Redis memory is cheap/abundant, we can increase the TTL.
If memory is constrained, we can decrease it.

---

## 5. Code Generation (SHA-256 + Timestamp, Base-62, 7 Characters)

**What:** Short codes are generated by hashing the URL + current nanosecond
timestamp with SHA-256, then converting the result to a 7-character base-62 string
(letters + digits only).

**Why:**

- **Timestamp** ensures that shortening the same URL twice at different times
  produces different codes.
- **SHA-256** gives a uniformly distributed hash.
- **Base-62** (a-z, A-Z, 0-9) avoids special characters that cause issues in URLs.
- **7 characters** gives 62⁷ ≈ 3.5 trillion possible codes — more than enough for
  most use cases.

**Trade-off:**

- There is a tiny **modulo bias** — each hash byte is modded by 62, and 256 doesn't
  divide evenly by 62, so some characters appear very slightly more often than
  others. This is negligible in practice.
- There is **no collision detection** — if two generated codes happen to match, the
  database INSERT fails due to the UNIQUE constraint, but the code does not retry
  with a different code. The request simply returns an error.

**When to reconsider:** At scale, if collision errors become noticeable, we can add
a retry loop that generates a new code on UNIQUE constraint violation.

## 6. Hexagonal (Ports & Adapters) Architecture

**What:** The business logic in `service/` depends only on Go interfaces defined in
`domain/ports.go` (called "ports"), not on concrete implementations like PostgreSQL
or Redis. The actual implementations (called "adapters") live in `adapter/driven/`
and are plugged in at startup in `cmd/server/main.go`.

**Why:** This lets us swap infrastructure without touching business logic — e.g.,
replace PostgreSQL with MySQL, or Redis with Memcached. It also makes unit testing
straightforward: we can mock the interfaces without needing a real database or cache
running.

**Trade-off:** For a small project like this, it adds more files and indirection
than strictly necessary. A simpler flat structure would mean fewer lines of code and
less navigation.

**When to reconsider:** For a quick throwaway prototype where testability and
swappability don't matter.

---

## 7. context.Background() for the Tracker Goroutine

**What:** The background click-tracking goroutine is started with
`context.Background()`, which **never gets cancelled**.

**Why:** The tracker needs to keep running even *after* the HTTP server shuts down,
so it can flush all pending clicks still in the channel to the database. If we used
the server's context, all `IncrementClicks` DB writes would fail the moment the
server starts shutting down — and we'd lose every click still in the queue.

**Trade-off:** The goroutine can't be cancelled via context; it only stops when
`tracker.Stop()` explicitly closes the channel. If someone forgets to call `Stop()`,
the goroutine runs forever (goroutine leak).

**When to reconsider:** If more complex lifecycle management is needed (e.g.,
multiple background workers that need coordinated shutdown).

---

## 8. Cache-Aside Pattern (Miss → DB → Backfill)

**What:** The caching strategy works like this:

- **On redirect:** Check Redis first. If it's a cache miss, query PostgreSQL, then
  write the result back to Redis so the next request is fast.
- **On create:** After saving a new URL to the database, immediately write it to
  Redis too (pre-warming).

**Why:** This is a standard "cache-aside" pattern. Redis lookups are sub-millisecond
while PostgreSQL queries take a few milliseconds. Pre-warming on creation ensures
that even the very first redirect for a newly created short URL is served from cache.

**Trade-off:** The first visit after a cache expiry is always slower (requires a
full database round-trip). There's also a tiny window where cache and DB could be out
of sync, though this doesn't matter here since URL mappings are immutable.

**When to reconsider:** If we add the ability to edit or delete URLs, we'll need
cache invalidation logic to prevent serving stale data.

---

## 9. Non-Fatal Cache Errors (Log and Continue)

**What:** If Redis fails (connection error, timeout, etc.), the error is **logged**
but the application keeps running — it simply falls back to querying PostgreSQL
directly.

**Why:** The cache is an optimization, not the source of truth. PostgreSQL has all
the data. Crashing the entire application because Redis is temporarily down would be
unnecessarily fragile.

**Trade-off:** If Redis goes down, *all* redirect traffic hits PostgreSQL directly,
which could overload the database. The application keeps serving requests, but
performance degrades significantly.

**When to reconsider:** We can add circuit breakers or alerts so the team knows when
Redis is down and DB load is spiking.

---

## 10. CGO_ENABLED=0 in Dockerfile

**What:** The Go binary is compiled with `CGO_ENABLED=0`, producing a **fully
static binary** with no runtime dependencies. It runs in a minimal Alpine container.

**Why:** Static binaries don't need libc or shared libraries installed in the
container. This allows using tiny base images (Alpine, or even `scratch`), resulting
in smaller Docker images and simpler deployments.

**Trade-off:** Some Go packages require CGO to work — for example, certain SQLite
drivers and advanced DNS resolution features. With CGO disabled, those packages
won't compile or will use fallback (pure-Go) implementations.

**When to reconsider:** If we need a CGO-dependent library (e.g., a C-based database
driver or machine learning library).

---

## 11. PostgreSQL RETURNING Clause

**What:** The INSERT query uses PostgreSQL's `RETURNING id, created_at` clause to
get auto-generated values back in the same query.

**Why:** Without `RETURNING`, we would need a separate SELECT after the INSERT to
get the generated `id` and `created_at` — two database round-trips instead of one.

**Trade-off:** `RETURNING` is a **PostgreSQL-specific** feature. MySQL uses
`LAST_INSERT_ID()` and SQLite uses `last_insert_rowid()`. This makes the repository
code not portable to other databases without modification.

**When to reconsider:** If we need to support multiple database backends (e.g., MySQL
for some deployments, PostgreSQL for others).
